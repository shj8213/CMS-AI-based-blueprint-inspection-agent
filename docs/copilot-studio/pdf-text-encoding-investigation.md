## 결론과 확인 범위

**같은 원본 PDF에서 한글이 깨지는 현상을 Windows의 pypdf로 재현했습니다.**
한글 글꼴 두 개에는 글자를 유니코드로 바꾸는 명시적 변환표(`ToUnicode`)가 없습니다.
대신 PDF에 기록된 `Adobe-Korea1` 문자 모음을 이용하는 추출기는 한글을 읽었습니다.
이 파일의 추출 호환성 문제이며, 글꼴 파일이 빠졌거나 이미지로만 된 PDF는 아닙니다.
`ToUnicode` 부재 자체가 모든 PDF에서 오류라는 뜻은 아닙니다.

**원본의 문자 코드에 맞는 변환표를 추가한 별도 복사본에서는 pypdf도 한글을 읽었습니다.**
화면 모양은 유지하면서 이 예제의 로컬 추출 문제를 개선할 수 있습니다.
원본 예제와 홈페이지·에이전트 지침은 변경하지 않았습니다.

11월 11일의 로컬 조사에서는 Copilot Studio를 실행하지 않았습니다.
11월 12일에는 사용자 로그인 후 브라우저의 Studio 미리보기에서 원본·보완본을 직접 시험했습니다.
미리보기에서 사용한 추출기, 원시 추출 문자열, 이미지 판독 도구의 원시 출력은 확보하지 못했습니다.
에이전트의 `Text is garbled (font encoding)`이라는
자체 설명만으로 내부 원인을 확정하거나 pypdf를 사용한다고 판단할 수 없습니다.

Windows에서도 재현되므로 macOS 사용자 환경만의 문제라고 볼 근거도 없습니다.

## PDF 내부 구조

| 글꼴 자원 | 종류·인코딩 | 임베딩 | `ToUnicode` |
| --- | --- | --- | --- |
| `/C1` | `.AppleSDGothicNeoI-Bold`, Type0, Identity-H | CIDFontType0C, 2,646바이트 | 없음 |
| `/C2` | `.AppleSDGothicNeoI-Regular`, Type0, Identity-H | CIDFontType0C, 5,820바이트 | 없음 |
| `/TT1`, `/TT2`, `/TT4` | `.SFNS` 계열, TrueType, MacRomanEncoding | 있음 | 없음 |
| `/TT3` | `.SFNS` 계열, TrueType | 있음 | 있음: 코드 `21` → `U+00B7` (`·`) |

표의 글꼴 이름은 부분 임베딩 접두사를 생략했습니다. 한글 글꼴의 하위 글꼴은
`CIDFontType0`이며, 둘 다 `CIDSystemInfo = Adobe / Korea1 / Supplement 0`입니다.
사용한 글자 모양을 담은 글꼴 파일 6개가 모두 PDF 안에 있습니다. 페이지의 이미지 자원은 0개이며,
글자 출력 명령과 벡터 도형이 들어 있습니다.

문제의 핵심은 **글자를 그리는 코드와 유니코드 문자가 같지 않다는 것**입니다.
제목의 첫 글자는 `/C1`의 `<043e>`로 기록됩니다. `Adobe-Korea1`에서 CID `043e`는
`가`(`U+AC00`)이지만 이를 그대로 UTF-16BE 문자로 해석하면 `о`(`U+043E`)가 됩니다.
`Identity-H`는 코드와 CID의 대응을 뜻하며 한글 유니코드라는 뜻이 아닙니다.

설치된 pypdf 7.0.1의 `_cmap._parse_encoding`은 `/Identity-H`를 `utf-16-be`로 처리하고,
`_parse_to_unicode`는 이 Type0 글꼴에 `ToUnicode`가 없으면 빈 변환표를 반환했습니다.
실제 추출에서도 제목은 `\u043e\u089a ...`로 시작하고 한글 음절은 0개였습니다.
이는 터미널 표시 오류가 아니라 추출 문자열 자체가 다른 문자인 경우입니다.

pdfminer.six의 `PDFCIDFont`는 `Adobe-Korea1`용 `PyUnicodeMap`을 대체 변환표로
사용했습니다. 실제 `to_unichr(0x043e)` 결과는 `가`였습니다.
PyMuPDF도 정상 한글을 추출했지만 내부의 세부 변환 경로까지 분석하지는 않았습니다.

## 재현과 보완 비교

환경: Windows, Python 3.11. 설치된 배포 패키지 버전은 pypdf **7.0.1**,
PyMuPDF **2.1**, pdfminer.six **20260107**입니다. 설치·업데이트는 하지 않았습니다.

| 도구 | 원본: 한글 음절 수 / 확인 문구 | 변환표 보완본: 한글 음절 수 / 확인 문구 |
| --- | --- | --- |
| pypdf | 0 / 0개 | 140 / 14개 |
| PyMuPDF | 140 / 14개 | 140 / 14개 |
| pdfminer.six | 140 / 14개 | 140 / 14개 |

확인 문구 14개는 제목, 단위, 제작·검사 금지 안내, 평면도, 구멍 중심, 중앙 관통 구멍,
두께, 재질, 공차·표면 거칠기, 미기재 설명, 설계 검증 자료가 아니라는 안내,
전체 크기, 표의 구멍 설명, 표의 재질·공차·거칠기 설명입니다.
공백·줄바꿈을 제외하고 문구를 대조했습니다. **모든 도면에 대한 정확도나 OCR 성능 점수가 아닙니다.**

원본을 144dpi로 그린 이미지와 추출 결과를 에이전트가 직접 대조한 주요 내용은 다음과 같습니다.
학생의 실제 동작 확인을 대신하지 않습니다.

| 실제 도면 위치 | 이미지에서 읽힌 표기 | 보완본 pypdf 결과 |
| --- | --- | --- |
| 왼쪽 평면도 치수·아래 정면도 치수 | 가로 80, 세로 40, 두께 5 | 숫자 보존 |
| 오른쪽 위 설명 | 구멍 중심: 왼쪽에서 40, 아래에서 20 | 같은 문구 |
| 오른쪽 위 설명 | 중앙 관통 구멍 1곳: 지름 8 | 같은 문구 |
| 오른쪽 중간 설명 | 재질: 미기재 / 공차·표면 거칠기: 미기재 | 같은 문구 |
| 오른쪽 아래 표 | 전체 크기: 80 x 40 x 5 | 같은 문구 |

숫자 `80`, `40`, `5`, `8` 등은 원본 pypdf에서도 남습니다.
하지만 한글 의미와 위치 관계를 읽지 않고 숫자만으로 검토가 성공했다고 볼 수 없습니다.
별도 지름 기호를 추측해 넣지 않고 원문인 `지름 8`로 대조했습니다.

### 보완 실험 방법과 유지된 내용

원본을 복사하여 `/C1`에서 실제 사용한 코드 25개, `/C2`에서 사용한 코드 63개에 대해서만
설치된 pdfminer.six의 `Adobe-Korea1` 변환표로 `ToUnicode`를 작성했습니다.
OCR 결과나 예상 문장을 역으로 끼워 넣지 않았습니다.
다른 PDF에 그대로 적용할 수 있는 범용 복구 도구가 아니라 이 예제의 원인 확인 실험입니다.

- 보완 파일: `tests/fixtures/simple-plate-example-tounicode.pdf`, 24,741바이트.
- 보완 파일 SHA-256: `9cef1cb0996eb50612503852ce5fc7a97fbfc01dd30cc03251a78bb9314270d7`
- 페이지 내용 스트림과 임베딩 글꼴 스트림의 바이트가 원본과 같습니다.
- PyMuPDF로 그린 144dpi(1684 × 1190), 288dpi(3368 × 2380) 이미지의 RGB 픽셀이
  각각 원본과 완전히 같습니다. 다른 뷰어 전체에 대한 보장은 아닙니다.
- 보완본 세 추출기의 비공백 문자별 개수는 원본 PyMuPDF 결과와 같습니다.
  추출기마다 읽는 순서·줄바꿈이 다르므로 문서 전체 문자열 순서까지 같다는 뜻은 아닙니다.
- 원본 파일의 바이트와 SHA-256은 변경하지 않았습니다.

다른 예제로 `simple.pdf`, `mixed.pdf`, `scan.pdf`도 세 도구로 추출했습니다.
앞의 두 파일에서는 `Hello blueprint`를 읽고, 스캔 페이지에서는 OCR 없이 본문 글자가
나오지 않았습니다. 이는 스캔의 정상적인 제한이며 이 파일의 한글 깨짐과는 다릅니다.
`simple.pdf`에서는 pypdf가 `incorrect startxref pointer(1)`와
`parsing for Object Streams` 경고를 냈지만 추출은 끝났습니다.
이 경고는 조사 대상 판 도면에서 발생하지 않았고, 관련 없는 예제는 수정하지 않았습니다.
비교 대상에 다른 생성기의 한글 PDF는 없으므로 다른 한글 PDF까지 일반화할 수 없습니다.

## 실행 방법과 기록

저장소 루트에서 다음 명령으로 원본 제목의 깨짐을 재현할 수 있습니다.
해당 패키지가 설치된 환경이 필요합니다. 일반 홈페이지 실행에 필요한 의존성은 아닙니다.

```powershell
python -c "from pypdf import PdfReader; print(ascii(PdfReader(r'tests\fixtures\simple-plate-example.pdf').pages[0].extract_text()))"
```

정상 한글을 읽은 대조 명령입니다. `ascii` 출력에서 `\uac00\uc0c1`은 `가상`입니다.

```powershell
python -c "import pymupdf; d=pymupdf.open(r'tests\fixtures\simple-plate-example.pdf'); print(ascii(d[0].get_text())); d.close()"
python -c "from pdfminer.high_level import extract_text; print(ascii(extract_text(r'tests\fixtures\simple-plate-example.pdf')))"
```

세 명령 모두 조사 시 실행해 위 결과를 확인했습니다.
글꼴 사전·내용 스트림 확인, 설치된 변환 코드 확인, Git 버전별 바이트 비교는
별도의 읽기 전용 Python 명령으로 수행했습니다.

세션 첨부 자료 `probe_pdf_text.py`는 원본 해시를 확인하고, 별도 결과 폴더에 보완 PDF,
추출 텍스트, 이미지, `pdf-text-probe-results.json`을 저장합니다.
저장소 루트에서 `python` 다음에 내려받은 스크립트 경로와 별도 결과 폴더 경로를 전달합니다.
이 스크립트는 저장소의 실행 코드나 기본 테스트에 추가하지 않았습니다.
원본·보완본 비교 실행의 최종 결과는 `all_checks_passed: true`입니다.

진단 중 실패도 기록합니다. 초기 코드 조회에서 pypdf 함수 이름을 잘못 지정해
`AttributeError`가 발생했고 `_parse_encoding`으로 고쳐 확인했습니다.
실험 스크립트 초기 실행에서는 존재하지 않는 `PdfWriter.add_object`를 사용해 실패하여
설치 버전의 `_add_object`로 고쳤습니다.
이어 추출기 전체 문자열의 동일 순서를 요구한 검사가 pdfminer의 배치 순서 차이로 실패했습니다.
문구 14개와 비공백 문자별 개수 비교로 나누고 이미지·스트림 비교는 유지한 후 재실행했습니다.
실패한 초기 실행을 통과로 세지 않았습니다.

`pdftotext`, `pdffonts`, `mutool`은 설치되어 있지 않아 실행하지 않았습니다.
11월 11일에는 홈페이지 자동 검사, macOS 비교 실행, Studio 원본·보완본 첨부 시험을 실행하지 않았습니다.
11월 12일의 Studio 실행은 아래에 별도 기록합니다.

## 해결 선택지와 이미지 판독의 한계

**우선 선택지:** 제작 원본이 있다면 한글을 유니코드로 추출할 수 있는 방식으로 PDF를
다시 내보내고 같은 문구와 화면을 비교합니다. 단순히 글꼴을 임베딩하는 것만으로는 부족합니다.
인쇄 방식으로 다시 저장하는 것만으로 해결된다고 보장하지 않으며, 글자를 윤곽선으로
바꾸거나 이미지로만 저장하면 오히려 본문 추출을 잃습니다.
이번 변환표 보완본은 원본 제작 문서가 없는 상태에서 로컬 개선 가능성을 확인한 비교용 자료입니다.
이 로컬 단계만으로 Studio 개선을 판단하지 않았으며, 후속 비교는 아래에 기록합니다.

**텍스트 추출이 계속 실패하는 경우:** 사용 가능한 도구로 실제 페이지 이미지를 열고,
전체 배치를 확인한 뒤 평면도 치수, 구멍 설명, 정면도 두께, 오른쪽 아래 표를 확대합니다.
원본을 읽기 어려우면 288dpi 이미지나 필요한 영역의 선명한 확대본을 요청합니다.
도구가 제공되지 않으면 이미지를 열었다고 주장하지 말고 그 제한을 알립니다.
OCR을 사용했다면 실제 사용 여부와 읽은 값을 원본과 대조한 상태를 구분합니다.

응답에는 실제로 확인한 범위, 읽은 원문, 읽지 못한 위치, 다음 확인 방법을 적습니다.
예를 들어 “1페이지 오른쪽 아래 표의 재질·공차 설명은 글자가 작아 판독하지 못함.
해당 영역의 확대본 필요”처럼 구체적으로 남깁니다.
숫자가 남았다고 그 의미를 추측하지 않으며, **읽지 못함을 도면에 없음으로 바꾸지 않습니다.**
기존 `reviewer-instructions-v3.txt`의 판독 불확실·확대 요청·부분 완료 원칙을 그대로 적용할 수 있습니다.
이 원칙이 실제 Studio 설정에 적용되어 있는지는 별도 확인이 필요합니다.

이번 로컬 예제의 이미지에서는 위 표의 내용과 안내 문구를 읽을 수 있었습니다.
그러나 이 결과는 Studio가 실제 이미지를 받거나 같은 해상도로 확대할 수 있음을 뜻하지 않습니다.
다른 도면의 흐린 글자·공차·작은 기호를 정확히 읽는다는 보장도 아닙니다.

검사해 통과했습니다. 원본·보완본 SHA-256도 다시 일치했습니다.
첫 로컬 확인 명령은 PowerShell 입력의 한글 비교에서 `AssertionError`로 실패했으며,
`$OutputEncoding = [System.Text.Encoding]::UTF8`을 지정해 재실행한 결과 통과했습니다.
저장된 UTF-8 응답 자체의 손상이나 PDF 문제로 기록하지 않습니다.
`git diff --check`도 통과했습니다. 앱 코드 변경이 없어 홈페이지 자동 검사는 실행하지 않았습니다.
응답 보관용 임시 로컬 서버와 브라우저 관찰 작업은 시험 후 종료했습니다.

**판단:** 이 예제에서는 문자 변환표를 보완했을 때 Studio의 글자 깨짐 보고가 사라지는 결과가
반복 관찰됐습니다. 원본에서의 깨짐 보고도 반복됐습니다.
다만 내부 추출기·원시 추출 문자열은 미확인이고 재시도는 같은 대화였으므로,
모든 PDF에 대한 해결이나 무조건적인 성공을 보장하지 않습니다.
응답 시간 초과는 별도 실행 한계로 남깁니다.
에이전트 설정 변경·게시·이슈 작성·종료는 하지 않았습니다.
커밋·PR 반영 대상은 이 조사 기록과 안내 링크, 별도 보완 PDF이며, 원본 PDF나 앱 코드는 변경하지 않습니다.
