2026-11-02 시험 시점에 기존 V1은 게시된 상태였고, V2는 **저장만 된 미게시 초안**이었습니다. V2를 저장한 뒤 새로고침하여 지침 내용이 유지되는 것을 확인했습니다. 이 파일들을 Git에 추가해도 Studio에 자동 반영되거나 게시되지 않습니다. Studio의 전체 에이전트 내보내기 파일도 아닙니다.

실제 도면·PDF·화면 캡처·실제 도면 검토 원문, 계정·환경·에이전트 식별자와 인증 정보는 포함하지 않았습니다. 가상 입력과 응답에 나오는 치수·재질은 실제 설계 자료가 아닙니다.

## 에이전트가 하는 일

도면 또는 ②의 읽기 자료를 근거로 필요한 정보를 스스로 도출합니다. 사람이 검사 목록이나 정답을 미리 알려 주는 방식이 아닙니다. `누락 후보`, `확인 필요`, `판독·연결 확인`을 구분하고, 각 판단의 위치·근거·한계·다음 확인 방법을 설명합니다.

V2는 다음 동작을 보완합니다.

- 작은 영역을 보지 못한 채 페이지 전체를 검토 완료로 처리하지 않습니다.
- 표의 행 제목과 실제 같은 행 값을 유지하며 계산값으로 원문을 고치지 않습니다.
- 품번이 건너뛴 것만으로 누락을 지적하지 않습니다.
- 치수의 대상이나 문자가 불확실하면 누락 또는 정상으로 확정하지 않습니다.
- 후속 검토에서 기존 항목 ID와 해소·철회 이유를 남깁니다.
- 사람 확인 상태는 항상 `미확인`으로 남깁니다.

웹사이트 자동 연결, ②→③ 자동 호출, 도면 수정·설계 승인·규격 적합성 인증은 구현 범위가 아닙니다. 저장소 홈페이지의 **도면 읽기**와 Studio의 **검토**는 별개입니다.

## Studio에서 가상 자료 시험을 재현하는 방법

이 순서는 승인된 Studio 환경과 에이전트 편집·시험 권한이 있는 팀원을 위한 안내입니다. 접근할 수 없으면 관리자에게 요청하고, 인증이나 권한을 우회하지 않습니다. 이 가상 자료도 Studio에 전송되며 사용량이 발생할 수 있습니다.

1. Studio에서 팀의 `도면 검토 에이전트`를 열고 빌드 화면의 지침을 확인합니다. 이미 다른 작업으로 수정된 지침은 덮어쓰지 말고 담당자와 먼저 확인합니다.
2. 적용이 승인된 초안에 `reviewer-instructions-v2.txt` 전체를 넣고 저장합니다. 게시하지 않습니다. 지침 끝 개행을 제외하면 6,312자이며, 저장 후 다시 열어 같은 내용인지 확인합니다.
3. 시험 당시에는 장기 메모리·웹 검색·조직 문서 검색·자동 에이전트 연결을 사용하지 않았고 Microsoft 인증을 유지했습니다. 재현을 위해 인증·권한·게시 설정을 임의로 바꾸지 않습니다. 도구의 종류와 사용 한도는 환경에 따라 다를 수 있습니다.
4. 미리 보기에서 **새 채팅**을 엽니다. 이전 도면이나 답이 남은 대화를 이어 쓰지 않습니다.
5. 아래 요청문 뒤에 `examples/reviewer-v2-probe-input.json`의 전체 내용만 붙여 보냅니다. 결과 파일, 아래 확인 표, 누락 목록이나 기대 정답은 보내지 않습니다. 이 시험에는 PDF·이미지를 첨부하지 않습니다.

   > 다음은 가상의 ② 형식 읽기 자료이며 원본 이미지/PDF는 제공하지 않았어. 이 자료를 검토하고 기존 구조의 JSON 하나만 출력해줘.

6. 응답이 끝나면 JSON 코드 블록을 별도 파일로 보존합니다. 저장소의 기존 응답을 새 결과로 덮어쓰지 않습니다. 문장·ID·개수가 완전히 같아야 하는 시험은 아니며 아래 동작과 근거를 대조합니다.

저장소 루트에서 아래 명령으로 두 JSON 파일의 문법을 확인할 수 있습니다. **저장된 파일을 검사할 뿐 Studio를 다시 실행하거나 의미의 정확도를 판정하지 않습니다.**

```sh

```

정상 종료하면 JSON 문법 검사를 통과한 것입니다. 오류가 있으면 출력된 오류를 해결해야 합니다. 홈페이지의 기존 DXF·PDF 읽기 검사 방법은 [저장소 안내](../../README.md#예제와-자동-검사)에 있으며, 이 Studio 가상 자료 시험과는 별개입니다.

## 여러 페이지·스캔 PDF 보완 (#32)

관련 이슈: [#32](https://github.com/shj8213/CMS-AI-based-blueprint-inspection-agent/issues/32)

V2 지침에 아래 동작을 더한 [reviewer-instructions-v3.txt](reviewer-instructions-v3.txt)를 추가했습니다. **이 파일을 Git에 올려도 Studio에 자동 반영되지 않으며, 담당자가 승인된 초안에 직접 넣어 시험해야 합니다.** V3를 게시하지 않았습니다.

- 모든 페이지를 확인하기 전에는 "없다"고 하지 않고, 다른 페이지에서 찾은 정보는 `not_missing`에 페이지 번호와 함께 적습니다.
- 흐려서 읽지 못한 정보는 `확인 필요`와 `[판독 미해결]`로 남기고 "없다"고 단정하지 않습니다.
- 선명하게 읽히고 모든 페이지에서 찾아도 없는 정보는 여전히 `누락 후보`로 이유와 함께 지적합니다.

| 시험 자료(가상 JSON) | 기대하는 동작 (정답을 에이전트에 보내지 않음) |
| --- | --- |
| [reviewer-v3-multipage-probe-input.json](examples/reviewer-v3-multipage-probe-input.json) | 1쪽 표제란의 재질이 비어 있어도 2쪽 부품표에 있으므로 재질을 "빠졌다"고 하지 않음. 어느 쪽에도 없는 폭·높이는 계속 지적 |
| [reviewer-v3-scan-probe-input.json](examples/reviewer-v3-scan-probe-input.json) | 번진 재질 칸은 `확인 필요`로 남기고 "없다"고 하지 않음. 어디에도 없는 폭·높이는 계속 지적 |

재현 방법은 위 V2 절차와 같고, 요청문 뒤에 해당 JSON 전체만 붙입니다. 저장소의 `tests/fixtures`의 PDF(`mixed.pdf`, `scan.pdf`, `scan-only.pdf`)는 홈페이지의 도면 읽기 검사용이며 이번 Studio 시험에는 쓰지 않았습니다.

- 가상 JSON 1건씩이며 이미지·PDF를 첨부한 시험이 아닙니다. 실제 스캔 PDF의 판독 능력은 확인하지 않았습니다.

- 흐린 정보의 `kind` 표기가 지침(`확인 필요`)과 다르게 나왔습니다. 후속 시험에서 일관성을 확인해야 합니다.
- 응답 JSON 문법은 이 문서 작성 시 저장 파일로 확인했으며 의미의 정확도를 판정한 것은 아닙니다. 반복 실행의 일관성은 확인하지 않았습니다.

완료 조건 중 "에이전트의 설명이 실제 도면과 맞는지 사람이 직접 비교"는 PR의 학생 확인란을 학생이 직접 채울 때까지 남아 있습니다.

## 쉬운 피드백과 JSON 형식 초안 (#51)

[reviewer-instructions-staged-v4.txt](reviewer-instructions-staged-v4.txt)는 ③의 지적을 **어디·무엇·왜·어떻게** 순서로 쉬운 한국어로 설명하고, `틀림`과 `확인 필요`로 구분합니다. 각 지적에 ②의 실제 항목 ID, 위치, 근거 자료, 확인 방법을 담도록 했습니다. 미리 보기 시험 전, Studio 지식에 실제 연결된 파일명이 `기계제도-기준자료-업로드용.txt`임을 확인해 지침의 파일명도 맞췄습니다. 기준 자료의 항목을 모든 도면에 강제하지 않으며, 판독 한계·불확실성·사람 확인 필요·설계 승인이나 규격 인증이 아니라는 제한을 유지합니다.

[examples/reviewer-v4-output-template.json](examples/reviewer-v4-output-template.json)은 필드 구조를 보여 주는 빈 틀입니다. 예시 판정이나 실제 도면 결과가 아닙니다. 필드 설명은 지침 파일에 있습니다.

2026-11-11, V4 지침을 `Contoso (default)` 환경의 ③ 에이전트에 저장하고 게시하지 않은 미리 보기에서 시험했습니다. 기존 모델과 지식 연결은 그대로 유지했습니다. 화면에서 지식 연결 파일명 `기계제도-기준자료-업로드용.txt`와 모델 `Claude Opus 5.5`를 확인했습니다. 에이전트는 저장되었고, 게시 상태는 바뀌지 않았습니다.

### 2026-11-12 축 도면 자동 연결 재시험

로컬 홈페이지에서 비기밀 축 비교 도면과 정상 기준 도면을 각각 ②→③에 전송했습니다. 두 시험 모두 사용자 동의 후 실행했습니다. ③ 요청에 같은 형상·항목의 명시 값을 서로 비교하고, 연결이 불확실해도 충돌을 `확인 필요`로 남기라는 보강 문장을 추가했습니다. 이 보강은 홈페이지가 보내는 요청에만 적용했으며, Copilot Studio의 저장된 지침을 바꾸거나 게시하지 않았습니다.

| 시험 도면 | ③ 응답 | 자동 분류 결과 |
| --- | --- | --- |
| 축 비교 도면 | `부분 완료`, 지적 8건 | 의도된 세 차이를 모두 언급했습니다. 전체 길이 160 대 165는 `틀림`으로 지적했고, 키홈 폭 및 베어링부 표기 차이는 각각 `확인 필요`로 남겼습니다. |

두 응답은 V4 JSON 파싱을 통과했고 `human_review_status`는 모두 `미확인`입니다. 정상 도면에서 에이전트가 `틀림`으로 출력한 수는 0이지만, 이것은 사람의 오탐 대조 완료를 뜻하지 않습니다. 열 개의 `확인 필요` 지적이 실제 도면에 근거하는지, 비교 도면의 세 지적이 각각 의도된 불일치와 정확히 같은 위치·대상인지 사람의 원본 대조가 남아 있습니다. 따라서 위 수치는 시험 결과 초안이며 #51의 사람 대조 완료 조건은 아직 충족되지 않았습니다.

로컬 브라우저 자동 검사는 <http://127.0.0.1:8000/tests/?agent=1>에서 38개 통과, 0개 실패였습니다. 이는 화면·연결·JSON 처리 검사이며 실제 도면 판정의 정확도를 검증하지 않습니다. Cloudflare 설정과 공개 배포는 하지 않았습니다.

2026-11-12 후속 수정에서는 [V4 지침 초안](reviewer-instructions-staged-v4.txt)과 홈페이지가 ③에 보내는 요청을 간결한 우선순위 방식으로 맞췄습니다. 제작·조립·검사 결정에 영향을 주는 핵심 지적만 남기고, 같은 부품·위치의 확인 사항은 묶으며, 단순한 표기 관행이나 조치에 영향 없는 의문은 `findings`에 늘어놓지 않습니다. 지적 개수 제한은 두지 않습니다. 2026-11-13 정상 기준 도면을 다시 실행한 결과 `검토 완료`, `확인 필요` 3건, `틀림` 0건이었습니다. 이전 응답은 `확인 필요` 10건, `틀림` 0건이어서 지적 수가 줄었지만, 사람의 원본 대조나 설계 적합성 확인을 뜻하지는 않습니다. 실제 Studio 저장 지침은 바꾸지 않았습니다.

### 정답표를 주지 않는 기준 중심 검토 방식 초안

2026-11-13 후속 검토에서는 답안이나 평가표를 에이전트 입력에 주지 않고, 판단 근거를 다음 세 층으로 나누도록 [V4 지침 초안](reviewer-instructions-staged-v4.txt)을 보완했습니다.

1. **도면에서 확인한 사실·계산:** 실제 표기와 계산식을 따로 적습니다. 예를 들어 구간 길이 합과 전체 길이가 같으면 그 결과를 기록하고, 그 사실만으로 설계가 올바르다고 확대 해석하지 않습니다.
2. **기준으로 확인한 문제:** 연결된 기준 자료나 공개 출제기준의 문서·적용 범위·정확한 요구사항을 실제로 확인한 경우에만 위반을 판정합니다. 기준 원문이나 적용성을 확인하지 못하면 조항이나 요구를 추측하지 않습니다.
3. **의도 확인 질문:** 같은 도면의 표기 대상이나 기능 의도가 불분명한 경우, 제작·조립·검사에 실질 영향이 있을 때만 `확인 필요`로 씁니다. 이는 결함 확정이 아니며, 단순한 호기심은 지적으로 만들지 않습니다.

JSON 구조는 그대로 두고, 확인 사실은 `summary`·`not_missing`, 근거가 확인된 문제와 영향 있는 확인 질문은 `findings`, 미확인 기준·범위는 `limitations`에 둡니다. ③ 요청에도 이 구분을 넣고 자동 연결 검사를 보강했습니다. 2026-11-13 같은 정상 기준 도면을 새 요청으로 다시 시험한 결과, 응답은 `검토 완료`, `틀림` 0건, `확인 필요` 3건이었습니다. 구간 길이 합과 전체 길이가 160 mm로 일치하고 ⌀25 k6·키홈 폭 8·길이 30의 반복 표기를 요약에 기록했습니다. 확인 질문은 (1) ⌀30·원주 흔들림과 기준 A의 연결, (2) 키홈 깊이·축 위치·단면 치수 8 및 단면 위치, (3) Ra 1.6·Ra 3.2의 적용 면으로 묶였습니다. 지적 수는 이전 간결화 시험의 3건에서 더 줄지 않았지만, 확인된 사실과 불확실한 질문이 요약에서 구분됐습니다. 실제로 확인한 근거는 연결된 기계제도 참고자료이며, 공식 KS 원문이나 공개 출제기준은 이번 시험에서 확인하지 않았습니다. 그러므로 기준 위반을 확인했다고 주장하지 않았고, 사람의 도면 대조 상태도 `미확인` 그대로입니다. 자동 브라우저 검사 38개는 통과했습니다. Studio 저장 지침을 바꾸거나 게시하지 않았습니다.

2026-11-14에는 의도 추정을 V4 JSON의 선택 필드 `findings[].intent_hypothesis`로 분리하고 결과 화면에도 따로 표시했습니다. 최신 코드를 불러온 홈페이지에서 가상 축 기준 PDF를 ②·③에 보내 실전 시험한 결과, `검토 완료`, `틀림` 0건, `확인 필요` 4건, `human_review_status: "미확인"`이었습니다. 네 지적 모두에 가능한 의도·도면 단서·다른 해석·확신 정도가 표시됐습니다. 예를 들어 `8×7`을 키 크기로 보는 해석, 단면의 `8`을 키홈 폭으로 보는 해석, 원주 흔들림을 ⌀30 바깥면과 축선 A에 연결하는 해석, Ra 값들을 바로 위 축면에 적용하는 해석을 후보로 제시했습니다. 키홈의 약 5 mm 위치 추정은 그림 비율에서 나온 값이라고 명시했으며, 도면에 적힌 치수로 취급하지 않았습니다. 이 후보들은 사람의 도면 대조나 설계 의도 확인을 대신하지 않습니다.

같은 시험에서 ③은 ②의 `source.file_name`에 서비스가 붙인 식별용 접미사를 근거로 파일명이 다르다고 적었습니다. 홈페이지 흐름에서는 같은 PDF가 ②와 ③에 전달되므로, 이 차이만으로 다른 파일이라고 결론 내리면 안 됩니다. 요청문과 초안 지침에 접미사를 불일치 근거로 삼지 말라는 규칙을 추가했고, 이를 자동 검사에서 확인했습니다. 이 보강 규칙은 아직 새 실전 전송으로 재시험하지 않았습니다. Studio에 저장된 지침을 바꾸거나 게시하지 않았고, 사람의 확인 상태도 바꾸지 않았습니다.

## DXF 도면 연결 (#33)

관련 이슈: [#33](https://github.com/shj8213/CMS-AI-based-blueprint-inspection-agent/issues/33)

② 지침은 DXF 해석 도구가 없으면 '미지원 형식'으로 답하게 되어 있습니다. 그래서 Studio 지침은 바꾸지 않고, 홈페이지의 기존 DXF 읽기 결과를 ② 형식 JSON(`schema_version` 1.1)으로 바꿔 ③ 도면 검토 에이전트에 붙여넣는 방식으로 연결했습니다. 사용 방법과 외부 전송 안내는 [저장소 안내](../../README.md#dxf-도면을-검토-에이전트에-보내기)에 있습니다.

이번 작업에서는 사용자가 선택한 **홈페이지 자료 복사 → Studio 수동 붙여넣기** 방식을 구현했습니다. 홈페이지에서 Studio를 호출하거나 파일을 자동 전송하지 않습니다. 이슈 원문의 제외 범위는 "웹사이트와 연결하기"이므로, 수동 복사 화면을 포함할지는 팀의 범위 확인이 필요합니다. 이 문서로 이슈의 범위를 임의로 바꾸거나 팀 합의가 끝났다고 처리하지 않습니다.

- 자료 앞에는 "원본은 제공하지 않았고, `limitations`에 적힌 읽지 못한 요소의 정보는 '도면에 없음'·'누락 후보'로 단정하지 말고 '확인 필요'로 구분해 달라"는 요청문이 붙습니다.
- `limitations`에는 읽기 기능의 지원 범위, 이 파일에서 실제로 건너뛴 DXF 요소 종류, 형상-치수 연결을 하지 않았다는 사실이 들어갑니다. 형식이 맞지 않거나 64자를 넘는 요소 이름은 그대로 안내문에 넣지 않고 `이름 확인 필요`로 남깁니다.
- ②의 전체 분석을 한 것이 아니므로 상태는 항상 `부분 완료`입니다. 좌표는 JSON으로 표현 가능한 원본 숫자를 반올림하지 않고 전달합니다.
- `raw_text`는 표시용 글자이며, DXF 전용 보조 필드 `dxf_raw_text`는 변환 전 글자 코드를 보존합니다. 기호 변환·MTEXT·정렬의 영향을 받는 글자는 `confidence: "중간"`, `needs_confirmation: true`입니다. 이는 해석하지 못한 서식을 복원하는 기능이 아닙니다.
- **아직 Studio에서 DXF 자료로 시험하지 않았습니다.** 2026-11-08 접근 시 로그인 화면으로 이동하여 실제 에이전트에 접근하지 못했습니다. 자료를 전송하거나 로그인·권한·게시·지침 설정을 바꾸지 않았습니다.

### 실제 시험과 기록

1. 기존 ③ 도면 검토 에이전트에 접근 권한이 있는 계정으로 로그인합니다. 에이전트가 없으면 담당 팀원에게 접근 권한을 요청합니다. 새 에이전트를 만들거나 지침·인증 설정을 바꾸지 않습니다.
2. 파일마다 **새 대화**를 열고 홈페이지에서 복사한 요청문과 JSON 전체만 전달합니다. 원본 파일을 첨부했는지, JSON만 전달했는지를 구분해 기록합니다. 이 시험에는 자동 전송이 없습니다.
3. 자료가 잘리거나 응답이 끝나지 않으면 미완료로 기록합니다. 실제 입력 길이 제한은 아직 확인되지 않았으며 임의의 허용 길이를 보장하지 않습니다.
4. 학생이 실제 도면과 응답을 대조하고 아래 항목을 #33에 기록합니다. 코드 검사나 AI의 비교를 학생 본인의 확인으로 바꾸지 않습니다.

기록 항목: 시험 날짜, 사용한 지침 판과 초안/게시 여부, 예제 파일, 입력 방식, 누락 후보와 이유, 확인 필요 항목, 맞는 지적·틀린 지적·판단 보류, 잘림·오류 여부, 사람이 대조한 범위. 계정·환경 식별자와 인증 정보는 기록하지 않습니다.

**에이전트 시험 기록 (2026-11-08, 학생 확인 아님):**
- 예제 `review-c.dxf`(선 1개, 글자 1개, 읽지 못하는 DIMENSION·INSERT 포함)를 게시된 ③ 에이전트의 새 테스트 대화에 전달했습니다.
- 입력 방식: 원본 파일 없이 요청문과 ② 형식 JSON만 전달했습니다. 줄바꿈을 없앤 압축 JSON(약 2,200자)이며 입력 중 "DXF 단위 표시: mm." 한 줄이 중복되었습니다(에이전트는 내용 차이 없음으로 처리).
- 응답: `부분 완료`, `확인 필요` 3건(치수·공차, 표제란·주서, 형상·뷰 구성). 읽지 못한 요소를 "도면에 없음"으로 단정하지 않았고, 원본 대조를 하지 않았다고 밝혔습니다. 잘림·오류는 없었습니다.
- `review-a.dxf`(약 6,800자 압축 JSON)와 `review-b.dxf`(약 6,300자)는 붙여넣기 방식으로 입력했습니다. 화면 반영이 몇 초~수십 초 늦었지만 전송되었습니다.
- A 응답: `부분 완료`. 확인 필요(구멍 관통·깊이, 공차·일반 공차 주서, 도면번호·수량)와 판독·연결 확인(TEXT 치수와 형상 연결, `%%c`→Ø 변환)을 냈습니다. 재질 SS400·단위 mm는 누락이 아니라고 보았고, 두께·재질을 빠졌다고 하지 않았습니다.
- B 응답: `부분 완료`. 빈 `재질:` 값, 판 두께 부재, 구멍 관통·깊이, 공차를 `확인 필요`로 지적했습니다. 읽지 않은 블록·DIMENSION·배치 공간에 있을 수 있어 "도면에 없음"으로 확정하지 않았고, 원본을 보지 않았다고 밝혔습니다.
- 위 응답은 에이전트의 출력일 뿐이며 사람이 원본과 대조한 결과가 아닙니다.

**남은 완료 조건:** 원본과의 사람 대조, 수동 복사 화면의 작업 범위 확인. 이 항목은 미완료이며 #33을 닫을 근거가 아닙니다.
